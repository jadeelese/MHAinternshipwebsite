1User story

Yours, verbatim:

"An MHA student in a program that's new enough that the internship and fellowship landscape is largely uncharted. They don't know what they don't know — and by the time they realize they should be applying, they're probably already behind on deadlines."

The site's single job is to catch that student before they realize they're late. If the first scroll doesn't do that, nothing else matters.

2The tier system — plain language

What a tier is. A confidence label on each listing. It tells us how sure we are this is a real opportunity an MHA grad can realistically land, versus a role we think might be one.

What it does. Two things at once:

  • A label on each listing — internal only, never shown to the user.
  • A gate on the search output: anything softer than tier 2 doesn't make it into listings.json.

How it links to search. The search methodology produces a candidate pile (maybe 150–200 possibles). The tier filter cuts anything that can't be verified. It's the quality floor that lets me ship a long list without stuffing it with maybes.

Search sources  →  Candidate pile  →  Tier filter  →  listings.json  →  Site

Tier definitions (operational, not aspirational)

Tier What qualifies Confidence
Tier 1 Employer and role named in a California MHA program's outcomes report (last 3 years), or explicitly named on the employer's own advanced-degree / MBA / MHA recruiting page. High
Tier 2 Employer has a documented advanced-degree pathway AND the role is in a healthcare-adjacent practice/division AND that practice has publicly hired graduate-degree holders in the last 2 cycles. Medium
Tier 3 Cut. Anything softer than tier 2 is not listed.

Every tier-1 and tier-2 condition is pointable: a specific URL, a specific PDF, a named role on a page. Nothing is "likely" or "probably." That's the discipline.

LinkedIn is explicitly not a verification source. Alumni on LinkedIn tell you where someone's degree once helped them get hired — not whether the firm is still recruiting from that program this cycle. We removed it per your call.

3How search is done — the methodology

Sources, in strict priority order. Higher-tier sources get checked first; lower-tier sources only fill gaps.

  1. California MHA program outcomes reports. Every accredited MHA program publishes an annual "where did graduates land" report — employer, role, location. Ground truth. Harvested where public.
  2. ACHE Administrative Fellowship Directory. ~100 post-graduate fellowships, filterable by state. All CA entries plus remote-friendly / nationally-recruiting entries.
  3. Employer career pages directly. Grad / advanced-degree sections of each firm's own site. The authoritative source for currently-open roles.
  4. NAHSE, NALHE, NCHL, Institute for Diversity in Health Management. Fellowship aggregators that cover programs ACHE often misses, especially diversity-focused tracks.
  5. BioSpace, HIMSS internship postings. Industry-specific aggregators for pharma/biotech and health IT.

Bucket minimums for v2

So the list doesn't lean on one industry:

  • ≥7 CA health system fellowships / internships
  • ≥5 CA payer / health plan internships
  • ≥7 consulting (MBB + Big 4 + healthcare boutiques)
  • ≥5 pharma / biotech
  • ≥5 digital health / health tech (non-engineering only)
  • ≥3 government / public sector
  • ≥3 non-profit / foundation
  • ≥3 post-grad administrative fellowships at non-CA-health-system orgs (VA, academic medical centers, national systems)

Total floor: ≥50 listings, all tier-1 or tier-2.

5Add-a-listing flow

v2 Human review via GitHub Issue

Shipping tonight. No new infrastructure. Uses what we already have.

  1. Student clicks "Add a listing" at the bottom of the home page.
  2. Button opens a pre-filled GitHub Issue on the MHAinternshipwebsite repo, using an issue template with three fields: Role title, Employer, Source URL (optional: brief note).
  3. Student submits the issue. GitHub automatically emails you a notification via your account settings.
  4. You open the issue in GitHub, decide:
    • Approve: add the listing to listings.json via the GitHub web UI (one commit, 60 seconds).
    • Decline: close the issue with a short comment.
  5. On approve → Vercel auto-deploys, listing is live.

You're always in the loop. Nothing goes live without your tap.

v3 Claude-powered automatic extraction, you still approve

Deferred. Needs two new environment variables (ANTHROPIC_API_KEY, GITHUB_TOKEN) and one Vercel serverless function. Build it when you want the submission form to feel instant.

The flow

  1. Student clicks "Add a listing" → three-field modal (Title, Employer, Source URL).
  2. POST to /api/submit (Vercel serverless function).
  3. Function fetches the URL, confirms HTTP 200 and that the employer name appears in the page content.
  4. Function calls Claude once: "Does this URL describe an internship or fellowship an MHA grad could realistically apply to? Return yes/no + 1-sentence reason + extracted fields (location, deadline, format, category)."
  5. If YES → function uses the GitHub API to open a pull request on listings.json with the extracted listing on a branch called submission/[hash]. PR body contains the student's note + Claude's reasoning.
  6. You get a GitHub notification. Review the PR. Click Merge (or Close) in the web UI.
  7. On merge → Vercel auto-deploys.

Difference from v2

  • Student sees "Added to the review queue — Jade will get to it soon" instead of being redirected to GitHub.
  • The listing is pre-structured by Claude, so your review is a one-click Merge for most of them.
  • Rate limit: one submission per IP per hour via Vercel KV.

Costs

  • Vercel serverless: free tier handles thousands of invocations.
  • Claude API: ~$0.003 per submission (one short call).
  • Vercel KV: free tier is sufficient.
  • Realistic monthly cost: under $1 unless the site goes viral.

v3+ Fully automatic (opt-in later)

Only consider this if submission volume ever gets large enough that queue review becomes a chore.

  • Claude extracts + validates + commits directly to main (no PR). You get a weekly digest email of what was auto-added, and you can revert any entry with one click.
  • Added only when there's clear demand. For now, you stay in the loop.

6Ship gate — what has to pass before merge

v2 You review the preview URL, then merge

Same gate as v1. When I open the v2 PR, Vercel builds a preview URL automatically. You open it, scroll, decide if it reads right. If yes, you click Merge in the PR. Production deploys from main.

No external reviewer. You're the gate.

v3 Automated gate — merge without you

When you want to stop clicking Merge every iteration, enable GitHub Actions on the repo. The actions run on every PR:

  1. Link check: every source_url in listings.json returns HTTP 200.
  2. JSON schema validation: listings.json parses and every entry has required fields.
  3. Build success: Vercel preview deploys without a console error on the home page.
  4. No HTML/CSS parse regressions.

If all four pass → auto-merge → production deploys. If any fail → PR stays open with a labeled error.

Enables you to go to sleep and wake up to new listings.

8What's deferred — the v3 shopping list

  • Claude-powered add-a-listing endpoint (see section 5) — needs ANTHROPIC_API_KEY + GITHUB_TOKEN as Vercel env vars.
  • Automated ship gate (see section 6) — GitHub Actions for link check + schema validation + build check.
  • Fully-automatic add-a-listing with weekly digest — only when submission volume justifies it.
  • Résumé-match client-side — paste a résumé, site ranks listings by fit. Runs in the browser, never leaves the device.
  • Anonymous flywheel — "N classmates applied here" counts, requires light auth.
  • Scheduled re-sweep — a bot that re-runs the search methodology quarterly and opens a PR with net changes.
  • Internal tier label visible on listings if a user requests it (power-user filter).
